# Appendix B: Known deviations from Apache Pekko

- A plain `restart` whose setup fails stops the actor. Pekko does the same when restarts are unlimited, but retries while a `with_limit` budget remains. Use `restart_with_backoff` for setups that can fail.
- An exception in a message adapter or `pipe_to_self` adapt function is logged and the message is dropped. Pekko delivers a `MessageAdaptionFailure` signal, which fails the actor unless handled. When the actor stops, `pipe_to_self` cancels the work it waits on: it closes a coroutine and cancels a future, even one other code awaits too. Pekko can't cancel a `Future`; its result goes to dead letters. Called from `PostStop`, `pipe_to_self` closes or cancels its work at once, and starting a timer does nothing; in Pekko the future still runs, and its result and the timer's messages go to dead letters.
- If a handler fails partway through `unstash_all`, the unprocessed messages stay in the buffer as in Pekko, but `resume` and `PreRestart` see the behavior from before the unstash began. Pekko tracks the intermediate behavior reached by the last successful message.
- Exceptions in `PreRestart` and `PostStop` handlers are logged, not supervised.
- Watching a message adapter watches the actor that owns it: `Terminated` carries the owner's ref, and the adapters of one actor share one watch, so `watch_with` on two of them with different messages raises `RuntimeError`. In Pekko each adapter is a ref of its own.
- `ask` and `ctx.ask` check the reply type but not that the target accepts the request, since the reply type is read from the request's `reply_to` field and pyright cannot tie both to one type parameter. `tell` is fully checked. Pekko checks both.
- The `Behaviors` factories double as decorators. This is only a Python spelling of the same call, so there is nothing to port, but Apache Pekko code has no counterpart to it. `ctx.pipe_to_self` and `ctx.ask` without `adapt` are decorators too, the Python spelling of the block Scala passes as their last argument. [Chapter 1](01-actors.md#decorators) lists every decorator.
- `ctx.timers` exposes the actor's `TimerScheduler` directly; Pekko hands it out only through `Behaviors.withTimers`. Both reach the same scheduler, and a restart cancels its timers either way.
- `start_timer_at_fixed_rate`, `StashBuffer.unstash(n)` and `Routers.group` are not implemented.
- Pekko's bounded mailbox only drops the new message. `overflow="drop_old"`, `overflow="fail"` (raise `MailboxOverflowError` in the sender) and the awaitable `offer` are additions. Adapted messages, timer messages and `pipe_to_self` results count against the capacity; they always use `tell`.
- `with_consistent_hashing_routing(mapping)` takes no virtual-nodes factor and routes with `hash(mapping(msg)) % size`, since a pool has a fixed size. The mapping may return any hashable.
- Paths use the `ohra://` scheme where Pekko's use `pekko://`, and the management extension is `Management` with `ManagementSettings` where Pekko's is `PekkoManagement`: the Pekko prefix is that project's name, as `akka://` and `AkkaManagement` were Akka's. An ohra node cannot join a Pekko cluster anyway, since the wire format differs (see the next entry).
- `StatusReply` is a frozen dataclass of `success_value` and `error_message`. An error made from an exception keeps it on its own node, but only its message crosses the wire, so another node sees a `StatusReply.ErrorMessage`, where Pekko serializes the throwable when a serializer for it is configured; its message is the exception's `str`. `from_try` uses the class name when that is empty, as Pekko uses the class name when the message is `null`. Java's `fromCallable` and `fromCallableKeepException` are not ported. `Done` is a class whose value is `DONE`. Both cross the wire under the manifests `ohra.Done` and `ohra.StatusReply`, which leaves the plain names to an app's own `@remotable` messages.
- Remoting is Artery narrowed to one layer: TCP with length-prefixed JSON frames, `@remotable` dataclasses instead of serializer ids and manifests, an unsendable message raises at `tell` instead of being logged and dropped, a restarted peer is served instead of quarantined, and there is no remote `watch`, no membership and no system-message delivery guarantee. `ask` across nodes works because the reply ref is given a temporary path on the asking node for exactly as long as the ask is pending. The outbound bound counts bytes, not messages: once connected, a `tell` to a peer that has left 16 MiB unread is a dead letter, where Pekko drops past `outbound-message-queue-size` (3072 messages), and `offer` waits for room instead. Remoting gzips every frame body over 32 KiB (`COMPRESS_ABOVE`), at level 6 with `mtime=0`, in both directions, and tells a compressed body by gzip's magic bytes, which JSON never starts with; Pekko compresses only Distributed Data's payloads, in its serializer, and Artery does not compress frames. `MAX_FRAME` (16 MiB) bounds the uncompressed body on both sides, and a compressed frame that inflates past it, is truncated, or has data after its end closes the connection. Compression runs inline on the event loop, so a 16 MiB frame holds the loop for under a second, as Pekko compresses inline on the sender's thread.
- TLS for remoting is Artery's `tls-tcp` with `RotatingKeysSSLEngineProvider` only, passed as `ActorSystem(ssl=...)` rather than by `ssl-engine-provider`. `ConfigSSLEngineProvider` is left out because it reads Java keystores, and so are a pluggable `SSLEngineProvider` and its `Setup`. `protocol`, `enabled-algorithms` and `random-number-generator` are not settings: the protocol is TLS 1.3, and Python's `ssl` cannot choose TLS 1.3 cipher suites, so OpenSSL's defaults apply. The default mount point reads `ohra-tls` where Pekko's reads `pekko-tls`.
- The cluster is Pekko Cluster narrowed to one data center, whose name is fixed at `default` (every member carries the role `dc-default`, as in Pekko, and there is no `data-center` setting): the gossip, vector clock, reachability table, convergence rule, leader election, member lifecycle, seed-node join processes, phi-accrual failure detector and heartbeat ring are ports of the Scala code, function for function. Roles travel in the `@remotable` JSON of `Member` and of the join, so a node of an earlier ohra version cannot join. A per-role minimum (`min_nr_of_members_of_role`) of 0 or less raises `ValueError`, where Pekko accepts it. The JOINING log lines leave out Pekko's app version. Left out: the app-version and config-compatibility checks on join and quarantine; the split-brain resolver is off unless `downing` is set, as Pekko without a provider. The heartbeat sender, the seed-node processes and the event publisher are state inside the one core daemon instead of separate actors, and the heartbeat receiver is its child. `ClusterSettings` replaces HOCON, with `allow_weakly_up_members` as a duration or `None` instead of a flag plus `weakly-up-after`. `Address` has no protocol field. `PrepareForFullClusterShutdown` is both the typed command and the daemon's internal `ClusterUserAction.PrepareForShutdown`, and it is not `@remotable`, which is fine because it only ever goes to the local daemon, as `Leave` and `Down` do. The statuses travel as the strings `"preparing_for_shutdown"` and `"ready_for_shutdown"` in `@remotable` JSON, where Pekko uses protobuf enum values 7 and 8; a node of an earlier ohra version cannot merge gossip that holds them. The member events do not check their member's status as Pekko's constructors do. The seed-node processes retry on a fixed-delay timer (the first seed every `min(1s, seed_node_timeout)`, the others every `seed_node_timeout`) rather than on Pekko's one-second task and `ReceiveTimeout`. The gossip target selector prefers nodes that have not seen the gossip with probability `gossip_different_view_probability` (0.8) up to `reduce_gossip_different_view_probability` members, which is what Pekko's settings document; Pekko's code passes the member count into the probability slot, so it always prefers such nodes in clusters of that size or smaller.
- The Receptionist has Pekko's API and semantics: a cluster node runs the port of `ClusterReceptionist` at `/system/clusterReceptionist`, on Distributed Data, and any other system runs `LocalReceptionist` at `/system/localReceptionist`. `Listing[T]` is a generic dataclass with fields rather than Pekko's untyped `Listing` with `serviceInstances(key)` accessors. Every system has a `/system` root, as Pekko's classic system does.
- The cluster receptionist keeps Pekko's control flow, with these differences. A `Deregister` of a ref that has no registration at all (never registered, or every registration already removed) is logged at error and ignored; Pekko's `removeLocalService` throws `IllegalArgumentException` and the receptionist stops. There is no join-time check of `distributed_key_count` (Pekko's `ClusterReceptionistConfigCompatChecker`), so the count must match on every node. Every `Update` replies to the system's `ignore_ref`, where Pekko sends it with no sender and the replies go to dead letters. The ddata key for index `i` is `ReceptionistKey_i` in creation order; Pekko indexes the key array of an immutable `HashMap`, so which ddata key a service key lands on differs from Pekko's even though `java_string_hash` matches, and ohra does not share the wire with Pekko. A local ref that is not an actor (a `FunctionRef` with no owner, say) is accepted by `Register` and `Subscribe` but never watched, so it is not removed when it stops. The tombstones are keyed by the path the ref has on the wire, since ohra paths carry no uid and the message adapters of one actor share a path; Pekko keys them by `ActorRef`, path and uid.
- A payload ref to a stopped or unknown local actor decodes to an `EmptyLocalActorRef` that keeps the path and sends to dead letters, as Pekko's. Pekko's reports `isTerminated`, so watching it delivers `Terminated` at once; in ohra only local actors can be watched, and `watch` of an `EmptyLocalActorRef` raises `TypeError`.
- Cluster sharding's coordinator keeps its state in Distributed Data, as Pekko's `DDataShardCoordinator`, on a Replicator of sharding's own at `/system/sharding/replicator`, or `/system/sharding/<role>Replicator` with a role. Membership events replace remote DeathWatch of regions. Left out: the other region queries (`GetCurrentRegions`; `GetShardRegionState`, `GetShardRegionStats` and `GetClusterShardingStats` exist), `ShardRegion.GracefulShutdown` (leaving or terminating runs it), custom allocation strategies and data centers. A proxy-only region is the `<type>Proxy` child of `/system/sharding`, as Pekko's, and is what `init` starts on a member without the shard role; since `init` is ohra's one API, `init` there also starts the coordinator's singleton manager when the member has the coordinator's role, as Pekko's classic `internalStart` does and Pekko Typed's `init` does not. Without a role, every member must call `ClusterSharding(system).init`: the coordinator's reads and writes count every member, and only `init` starts a member's `/system/sharding/replicator`. `rebalance_absolute_limit` 0 means no absolute cap (in Pekko, 0 selects its older allocation algorithm). The coordinator lives at `/system/singletonManager<type>Coordinator/singleton/coordinator`, where Pekko's is `/system/sharding/<type>Coordinator/singleton/coordinator`, since ohra's singleton managers are `/system/singletonManager<name>`. A region may register while its member is Up, Leaving, Exiting, PreparingForShutdown or ReadyForShutdown, where Pekko's coordinator accepts Up only, so a region can re-register after a coordinator move during its own leave. A coordinator that throws restarts at once, as under Pekko's `BackoffOpts.onStop`, and reads its state again; it tells its regions to register again, as it does when it stops, in place of their remote DeathWatch of it. A coordinator that stops, as when its remember-entities store stops, is started again after `coordinator_failure_backoff` (up to 5 times it, with a 0.2 random factor), as under Pekko's `BackoffOpts.onStop`, and stops for good only on its stop message. The regions send their registration to every member up to the first Up one, as Pekko's `coordinatorSelection`. A region told that a shard it hosts now lives on another region logs an error and hands its copy off, where Pekko's region throws.
- Passivation strategies: `PassivationStrategySettings` and the strategies it resolves to (idle, least recently used, segmented, most recently used, least frequently used and the composite) are ported, and the shards run them. With `remember_entities` on it resolves to no passivation, as Pekko's. There is no HOCON: `default-idle-strategy` and `default-strategy` are the constants `PassivationStrategySettings.default_idle_strategy` and `default_strategy`, a custom named strategy is built with the builders, durations are float seconds and proportions are tuples (a list given to `with_segmented` or `with_proportions` is stored as a tuple). Where Pekko overloads a builder, one method takes a union: `with_idle_entity_passivation` a timeout or an `IdleSettings`, `with_segmented` a number of levels or the proportions. The companion `apply`s are `create` static methods and the Java DSL variants are not ported. The region logs the strategy at start as Pekko's does, with durations printed as `120 s` where Pekko prints `2.000 min`. `ClusterShardingSettings.passivation_strategy` is computed on access. The strategies take a clock function in seconds, the scheduler's when the shard runs them, so `ManualTime` can drive them, where Pekko uses its `Clock` extension in nanoseconds, and there is no `scheduled-clock-interval`. The recency and frequency lists in `ohra.util` keep Pekko's order on `OrderedDict`s and a sorted priority list in place of linked lists, and their iterator methods return snapshots; the frequency sketches hash string ids only, as Pekko's only `Hasher` does, bit for bit as Java's `String.hashCode` and Scala's MurmurHash3, and `toDebugString` is not ported.
- The sharding coordinator on Distributed Data differs from Pekko's `DDataShardCoordinator` in these ways. A region entry in the state carries its node's `UniqueAddress`, since ohra paths carry no uid: a region whose node is not a current member is terminated when the state is loaded, a registration at a recorded path from another incarnation terminates the old entry first, and a removed member terminates only the regions recorded for its incarnation. A region proxy's entry carries its node's `UniqueAddress` too, and a proxy is dropped when it says it stopped (`RegionStopped`, which a local proxy's watch also gives) or its member is removed, in place of Pekko's DeathWatch. The coordinator sends one state update at a time: when one message causes two (the loaded state holds two gone regions), the second waits for the first to succeed and its write includes the first change, where Pekko sends both from the same base and the second write can miss the first's change. Regions loaded from the stored state count as alive before they register again, where Pekko adds a region only on `Register`; so a loaded region that never registers still waits the down-removal margin when its node is removed. They count toward the minimum of `hasAllRegionsRegistered` too, so a coordinator that takes over with enough live regions in its state allocates at once, where Pekko's waits until that many have registered with it again. The stash is bounded at 100,000 messages, where Pekko's classic `Stash` is unbounded, and the `GetShardHome` requests held while the state loads or an update is in flight are a queue in arrival order without duplicates, where Pekko's `Set` has no order. When the remember-entities state arrives while the loaded state initializes, the coordinator keeps it and allocates those shards when the state is initialized; Pekko's `waitingForStateInitialized` (ShardCoordinator.scala 1686-1687) builds the new state and discards it, so that coordinator never starts them proactively. A supervised restart of the coordinator drops its stash without dead letters, where Pekko's classic `Stash` puts the stashed messages back in the mailbox before the restart (`preRestart` calls `unstashAll`); the regions retry what was lost, and the restarted coordinator reads its state again. The Replicator is reached through one `ReplicatorMessageAdapter`, whose ask timeout (the larger of `waiting_for_state_timeout` and `updating_state_timeout`, plus one second) covers both the Get and the Update, where Pekko tells the Replicator directly with no ask.
- Each of sharding's Replicators (one per role, and the role-less one) is spawned by the first `init` that needs it, with that entity type's `distributed_data` (`None` takes the cluster's with `prefer_oldest=True` and `max_delta_elements=5`, and its durable keys are empty unless `remember_entities` is on, when they default to `shard-*`); a later `init` on the same Replicator with different `distributed_data` settings has them ignored with a warning (the entity type still starts), where Pekko's guardian reads one set from config.
- The sharded daemon process is Pekko's `ShardedDaemonProcess.init` for a fixed number of processes: `initWithContext` and the rescaling commands (`ChangeNumberOfProcesses`, `GetNumberOfProcesses`) are not ported, so `init` returns nothing, and there is no `shardAllocationStrategy` parameter. `ShardedDaemonProcess` is a plain class built on each call, as Pekko's impl keeps no state either. `ShardedDaemonProcessSettings` is a frozen dataclass in seconds rather than HOCON; with no `sharding_settings` the daemon starts from `ClusterShardingSettings()`, as Pekko's `sharded-daemon-process.sharding = ${pekko.cluster.sharding}`. `keep_alive_from_number_of_nodes` is kept but unused, as in Pekko 2.0's code. `ShardedDaemonProcessContext` is a frozen dataclass where Pekko's is a trait. The replicated state's `started` is epoch seconds where Pekko's is an `Instant`, and the state and its key go on the wire as `ShardedDaemonProcess.State` and `ShardedDaemonProcess.StateKey`. The coordinator's `sharding_ref` is an `ActorRef[StartEntity]`, since the region takes the typed `StartEntity` itself, where Pekko's is an `ActorRef[ShardingEnvelope[T]]` used through `toClassic`.
- CoordinatedShutdown has Pekko's phases as a fixed list and `CoordinatedShutdownSettings` in place of HOCON: no custom phases or dependency graph, `recover` always on, no `exit-jvm`, `exit-code` or reason overrides. The signal hook is opt-in through `run_on_signals` where Pekko's JVM hook is on by default; its reason keeps the name `JvmExitReason`, and the handler owns the signal for the whole event loop (Python handlers do not compose as JVM hooks do): use it only when the system owns the process's signals, and under a server such as uvicorn call `system.terminate()` from the server's shutdown hook instead. A phase that times out cancels its still-running tasks, where Pekko lets them run on; a task that swallows the cancellation holds the run. A guardian that stops on its own runs the phases after its actors are gone, where Pekko Typed's guardian wrapper runs them before. There is no `ClusterJoinUnsuccessfulReason`, since there is no `shutdown-after-unsuccessful-join-seed-nodes`. The cluster-leave task subscribes with an adapter rather than Pekko's `CoordinatedShutdownLeave` child actor.
- Pekko Management is narrowed to the Kubernetes path and the standard library: the endpoint is a small HTTP/1.1 server (GET only, one request per connection, no HTTPS) and probing and the API call use a matching client, so Pekko's TLS client for probing is dropped; settings objects replace HOCON and class-name loading (`routes`, `*-checks`, `join-decider.class`, `discovery-method`); only `KubernetesApiServiceDiscovery` and `ConfigServiceDiscovery` exist; each member's roles are a sorted list where Pekko emits a set; the mutating cluster routes answer 405 with no switch, and there is no `/cluster/domain-events` stream; the bootstrap starts from `Management.start()` rather than as an auto-started route provider; `ResolvedTarget.address` is a string. Pekko's per-host fallback-port filter is kept, so several nodes on one host need `filter_on_fallback_port=False`, as the example does.
- The split-brain resolver is Pekko's SplitBrainResolver and DowningStrategy without data centers, the lease-majority strategy or quarantine's `DownSelfQuarantinedByRemote`. It ticks every `min(1 s, stable_after / 4)` rather than a fixed second, so millisecond settings work. `SplitBrainResolverSettings` and the strategy dataclasses replace HOCON (`active-strategy`, `stable-after`, `down-all-when-unstable`, `static-quorum.quorum-size`, `keep-oldest.down-if-alone`, and each strategy's `role`); `down_removal_margin` is a `ClusterSettings` field, and the resolver is turned on with `downing=` rather than `downing-provider-class`. It is a child of the core daemon at `/system/cluster/downingProvider`, and its failure shuts the node down, as in Pekko.
- The cluster singleton is ClusterSingletonManager and ClusterSingletonProxy without the lease or data centers; the oldest-changed tracker is state in the manager rather than a child actor. The proxy finds the instance with an `IdentifySingleton` message to the manager on the oldest member, answered with the instance ref, in place of `Identify` to the instance's path; it keeps asking every `singleton_identification_interval` after it has found it, in place of remote DeathWatch, so a dead instance is noticed within one interval. Hand-over messages carry an explicit `from_` ref. The actors are `/system/singletonManager<name>` and `/system/singletonProxy<name>`, without Pekko Typed's `-no-dc` suffix on the proxy.
- `ctx.stop(child, after_pending=True)` queues the stop behind the child's pending messages, like classic Pekko's `PoisonPill`; Pekko Typed has no public equivalent. During a backoff it waits for the restart, as Pekko's `RestartSupervisor` stashes a typed `PoisonPill`. `Sharding` uses it so passivation never drops a message the region already forwarded.
- Persistence is ohra's own shape, not `DurableStateBehavior`, and there is no event sourcing; see [How this differs from Apache Pekko persistence](03-persistence.md#how-this-differs-from-apache-pekko-persistence). The default codec is pickle; Pekko uses its serialization extension. Its recovering and persisting states follow Pekko's `Recovering` and `PersistingState`, with these narrowings: `stash_capacity` and `recovery_timeout` are parameters, not config; a full stash only drops (Pekko's `fail` overflow strategy isn't ported); a store failure fails the actor with the store's own exception, not wrapped in a `DurableStateStoreException`; there are no recovery permits. Signals other than `PostStop` and `PreRestart` that arrive during a store call are held and delivered after it, where Pekko calls the signal handler at once with the visible state; `PostStop` and `PreRestart` go to the behavior before the write, ohra's equivalent of that visible state. Commands stashed during a failed store call survive a restart, where Pekko's internal stash is recreated; during a backoff they join its stash even past the backoff's `stash_capacity`, and `resume` after a failed write carries on with the behavior before it; Pekko doesn't resume a `DurableStateBehavior`.
- `StopShards` is public and carries a `reply_to` for the `ShardStopped` acks, where Pekko's is in `ShardCoordinator.Internal` and acks the sender; ohra's messages carry no sender. Its request ids are `uuid4().hex`, and its log lines list the shards in sorted order.
- `Entity.with_message_extractor` returns `ExtractedEntity[M, E]`, a subclass of `Entity[M]`, where Pekko's `Entity[M, E]` has the envelope type as its second parameter: Python 3.12 has no defaults for type parameters, so `Entity[M]` cannot default `E` to `ShardingEnvelope[M]`. `ClusterSharding.init` and `Sharding.init` type the region of an `ExtractedEntity` as taking `E`. The region tells an extractor's message from its own by type, after its own messages, as Pekko's classic region matches its own messages before the extractor's.
- `Sharding.init` is `ClusterSharding`'s region and Shard on one node, with no coordinator; `ClusterSharding(system).init` adds the coordinator, remote homes and rebalancing. The single-node region ref is passed to `entity_ref_for` explicitly since there is no extension registry. `with_buffer_size` replaces Pekko's buffer-size setting and wins over that of `with_settings`, whichever is called first. Passivation is Pekko's strategies, and idle is checked on an interval of half the timeout by default, as in Pekko. The region answers `GetShardRegionState` and `GetShardRegionStats` through a short-lived child actor that asks every Shard, not through a separate query ref. The type of the region's messages includes `SetActiveEntityLimit` and `GetShardRegionStats`, so code that writes it out must add them.
- The Shard is Pekko's `Shard`, and differs in these ways. `dropBufferFor`, which Pekko never calls, is not ported. `verbose_debug_logging` and `fail_on_invalid_entity_state_transition` are `ClusterShardingSettings` fields, where Pekko reads them from the system's config. The lease's owner is `system@host:port`, and on a system with no cluster it is the system name. The shard awaits its lease's `release()` in `PostStop`, bounded by the lease's `operation_timeout`, where Pekko releases without waiting. Until the shard has terminated its region still routes to it, so messages for that shard in the window are dead letters; after a lost lease the release is the call most likely to take the whole timeout. The lease-lost reason is shown with `repr()`. The `HandOffStopper` stops entities through the shard's context, since ohra stops children only: with no stop message it stops them after their pending messages and names that `PoisonPill` in its warnings, and with one it names the message by its Python class. Its warning prints `5 s`, and the region's query warning prints its timeout as `3 s`, where Pekko prints `3 seconds`. Single-node `Sharding` forwards to a shard that is still waiting for its lease, and the shard stashes; the cluster region buffers until `ShardInitialized`, as Pekko's does. On a system with no cluster a shard gets no member events, so it never prepares for shutdown. `initialize_shard` delivers to the shard registered under that id, not to the message's sender.
- Remembered entities are Pekko's with `remember-entities-store = ddata`, and differ in these ways. The event-sourced store and custom stores are left out, since ohra has no event sourcing, and `remember_entities_store` takes only `"ddata"`. `Sharding.init` refuses `remember_entities` with a `ValueError`, as the single-node region has no Replicator. The public `StartEntity` is in the type of the region's messages, and the region wraps it as `ShardingEnvelope(id, StartEntity(id))`, where Pekko Typed's region casts it to the envelope. That envelope is never acked, as Pekko Typed has no ack; the starter's start is the internal `_StartEntity`, Pekko's classic `StartEntity` with its sender, which carries `ack_to` and is acked with `StartEntityAck`. While an entity is in `RememberingStop`, the shard stashes a `_StartEntity(entity_id, ack_to)` where Pekko stashes the message it received, so an enveloped `StartEntity` is replayed through `start_entity`. An enveloped `StartEntity` that arrives while a write is in flight is batched only for an entity with no state, and for any other it is handled as a direct start, where Shard.scala 1061-1066 batches it whatever the state, so a `StartEntity` for a running entity would crash the shard. The starter takes its batches in `sorted(ids)` order, as the order of Pekko's `Set.splitAt` is unspecified. Typed has no sender, so the shard's verbose stash logs, while it waits for its lease or its remembered entities, leave out Pekko's "from [sender]". Every shard, remembering or not, is restarted on a failure by a supervisor inside its own behavior, where Pekko's region restarts it by the classic default, and it keeps its stash across the restart, where Pekko's `preRestart` puts the stash back in the mailbox. The shard's store and the coordinator's store are spawned under restart supervision, the classic default. The region restarts a remembering shard that stopped without a hand-off with a timer keyed `("RestartShard", shard_id)`, where Pekko uses `scheduleOnce`, so a second stop within `shard_failure_backoff` replaces the first timer and a restart of the region cancels it. The region deletes its `region_by_shard` entry for a terminated local shard, where Pekko keeps it, so a remembering shard restarts only once the coordinator answers `GetShardHome`, and the buffered `RestartShard` is dropped with the debug log "Dropping buffered message". Pekko's specs that change the shard id extractor are ported as a change of `number_of_shards`, the default extractor's parameter, and the region's warning for an extractor that does not handle `StartEntity` is left out: it is for classic extractors, and Pekko Typed's `ExtractorAdapter` handles `StartEntity` for every extractor, as ohra's region does.
- The stats queries go to the region, as `GetShardRegionState` does: there is no typed `shardState` actor and no entity type key, so the typed `GetClusterShardingStats` is `region.tell(GetClusterShardingStats(timeout, reply_to))`, and the ref `ClusterSharding(system).init` returns takes the queries and `SetActiveEntityLimit` besides the envelopes. It still passes where an `ActorRef[ShardingEnvelope[M]]` is expected. `ClusterShardingStats` keys its regions by the address in their path. `MessageBufferMap` holds messages without senders and has no `drop`. Dropped messages are published as `Dropped` on the event stream, as Pekko's. A log that prints `null` in Scala prints `None`.
- `ohra.ext.fastapi` is not in Pekko; it is the lifespan, dependency and 504 mapping that every FastAPI app over actors otherwise writes by hand. Its `actors.websocket` follows Play Framework's `ActorFlow.actorRef`: buffer size 16, `OverflowStrategy.fail`, and a wrapper that spawns the connection's actor, watches it, and stops it behind its pending frames when the socket closes, as Play's `PoisonPill` does. It differs in that the wrapper ends `out` itself when it stops (Play's actor sends `Status.Success`), the frames already told are sent before the socket closes, a `decode` function reads incoming text frames where Play has a message flow transformer, frames go out as JSON, and the socket is closed with 1008 when the client falls behind and with 1003 when `decode` rejects a frame. The wrapper is an anonymous child of the guardian, so it shows up in the guardian's `ctx.children`. `terminate()` drains the open connections in the coordinated shutdown's `service-stop` phase, as Pekko HTTP's graceful termination does: each connection's actor stops, and the phase waits, up to its timeout, for the frames already told to go out and the socket to close with 1000. With `run_by_actor_system_terminate=False` there is no such phase, so terminating drops the unsent frames and closes with 1001. A socket still blocked in `ws.send_json` when the phase times out (a peer that stopped reading, short of the overflow limit) closes only when that write returns.
- Streams run fused: the whole graph is one task, which the stream's actor under `/system/Materializers/StreamSupervisor` starts. There are no `.async` boundaries, no attributes and no input buffers between stages. A stage that races its upstream pull against something else (`map_async` and `ActorFlow.ask`, `merge`, `zip`, `grouped_within`, the kill switch, `Sink.queue`, `ActorSink`) runs each upstream `__anext__` in an asyncio task of its own, so an async generator upstream of one that holds `asyncio.timeout(...)` or a `TaskGroup` across a `yield`, or writes contextvars, does not see them as it would in a plain `async for`. For the same reason, when such a stage is cancelled while its pull is suspended inside the generator, the generator sees `CancelledError` at that await rather than `GeneratorExit` at a `yield`: cleanup belongs in `finally`, which runs either way, not in `except GeneratorExit`. A source whose `aclose()` raises while the stream cancels it (a generator whose `finally` raises, or one that ignores `GeneratorExit`) does not fail the stream: the error is logged on `ohra.stream.dsl`, as Pekko logs a stage that fails in `postStop`. So is a hand-written iterator whose `aclose()` raises after it completed, where Pekko's `unfoldResource` fails the stage when its `close` throws. A source that never suspends hands the loop back every 1000 elements, Pekko's `sync-processing-limit`. The system is passed to `run(system)` explicitly where Pekko takes an implicit `Materializer`, and there is no `Materializer(ctx)`: a stream run from an actor is not stopped with that actor.
- Not ported from Pekko Streams: `GraphDSL` and the junctions (`Broadcast`, `Balance`, `Partition`, ...), `merge`, `zip` and `concat` covering the common fan-in; `ActorAttributes.supervisionStrategy` (resume and restart), with `recover` and `recover_with_retries` ported; `SourceWithContext`, and with it `ActorFlow.askWithContext`; `ActorFlow.askWithStatus`; `PubSub` (ohra has no `Topic`); `ActorSource.actorRefWithBackpressure`; and the stream test kit (`TestSource`, `TestSink.probe`).
- `collect` and `recover` take a function that returns `None` to skip an element or to rethrow, in place of a partial function, so a `collect` function cannot emit `None`. `NotUsed` and `Done` are classes whose values are `NOT_USED` and `DONE`. `Flow.of(int)` is javadsl's spelling, since Python has no `Flow[Int]` apply.
- `concat` is Pekko's `concatLazy`: the second source is not pulled until the first has completed, where Pekko's `concat` is detached and pulls it at materialization. `merge` and `zip` pull their inputs from the first downstream pull, where Pekko's pull every input at materialization, and `zip` pulls both inputs again only on the next downstream pull, where Pekko's pulls the next pair as soon as it has pushed one.
- `throttle` is shaping mode only, with no `ThrottleMode.Enforcing` and no cost function. Its token bucket is Pekko's `TokenBucket` in integer nanoseconds on the scheduler's clock, which is why the `Scheduler` protocol has `current_time`. `grouped_within` counts elements (every weight is 1) and re-arms its timer with `schedule_once` after each group, where Pekko restarts a fixed-delay timer. `Source.tick` runs on `schedule_with_fixed_delay` and drops a tick that finds no pull waiting, as Pekko's `TickSource` does.
- A kill switch completes or fails its stream at once. An element whose pull completes in the same event-loop round as the switch is dropped.
- `Source.queue` and `Sink.queue` take one concurrent `offer` and one concurrent `pull`, Pekko's default `maxConcurrentOffers` and `maxConcurrentPulls`, and neither is a setting. An `offer` to a queue whose stream has ended answers `QueueClosed`, where Pekko fails it with `StreamDetachedException`; on `fail()` or an overflow failure, the offers still waiting are answered `QueueClosed`, where Pekko leaves them unresolved. `SinkQueue.pull()` after `cancel()` returns `None`, where Pekko fails it with `StreamDetachedException`. `Sink.queue` does not prefetch: it pulls upstream only when `pull` is called. `SinkQueue` is also an async iterator. The four results are reached only as attributes of `QueueOfferResult` (`QueueOfferResult.Enqueued`, `.Dropped`, `.QueueClosed`, `.Failure`), and none is exported from `ohra.stream` on its own, since `Failure` and `Dropped` are already ohra names.
- `ActorSource.actor_ref` fails its stream at once, unpulled, only for the stage directly below it, which is where `watch_termination` has to sit to see an overflow at once (`ohra.ext.fastapi` puts it there); further down, the failure arrives with the next pull. Its ref is not an actor and can't be watched, where Pekko's is the stage actor that stops when the stream ends. Dropped elements are logged, as in Pekko, not published as `Dropped` on the event stream, and tells after the end are logged on `ohra.dead_letters`, not published as `DeadLetter`. A burst into a waiting consumer fits `buffer_size` elements where Pekko's fits one more, since Pekko pushes the first element straight to the pulled outlet and ohra counts it until the consumer takes it. A completion always drains the buffer (Pekko's `CompletionStrategy.draining`).
- Only local refs can be watched, so `ActorSink` to a remote ref never completes when that ref stops, and `ActorFlow.ask` to a remote ref relies on its timeout. `ActorFlow.ask` fails with `WatchedActorTerminatedError`, Pekko's `WatchedActorTerminatedException` with the same message. `ActorSink.actor_ref_with_backpressure` ignores acks that arrive after the stage has ended, where Pekko's stage actor would dead-letter them.
- `terminate()` fails the materialized futures of the streams still running with `AbruptStageTerminationError`, as Pekko's `AbruptStageTerminationException`, and `run()` on a terminated system raises `RuntimeError`. A stream's actor stops only once the stream has torn down: the stream is cancelled once, and `terminate()` waits for its asynchronous cleanup, such as a source's `finally`, up to `TEARDOWN_TIMEOUT` (1 s), then cancels it again. Pekko's `postStop` is synchronous and does not wait for a close that returns a future.
- Handlers may be `async def`; Pekko's are synchronous. An await in a handler holds the actor, as a blocking `Await.result` would hold a Pekko actor's thread: no other message, a stop included, is handled until it returns, so an await that can stall needs `asyncio.timeout` or `ctx.pipe_to_self`. [When a handler may await](01-actors.md#when-a-handler-may-await) has the cases.
- `batching` is not in Pekko. It flushes a pending batch in `PostStop` and keeps the batch in a closure-local list.
- Only local refs can be watched. A bridge to a JVM Apache Pekko system over TCP is possible but deferred until there is a caller for it.
- The test kit's waits are awaited, where Pekko's block the test thread, and spawning and creating a probe are not, as in Pekko. Its names are importable from `ohra.testkit` only, not from `ohra`, since Pekko ships the test kit as a module of its own. Not ported: `BehaviorTestKit`, `TestInbox`, `LoggingTestKit`, `SerializationTestKit`, the `PF` variants such as `fishForMessagePF` (a fisher's `match` covers them) and `expectMessageClass` (the Java spelling of `expect_message_type`). A fisher that returns no outcome fails the test as Pekko's `MatchError` does.
- The event stream is Pekko Typed's `EventStream` commands over an actor of its own, narrowed to what the runtime publishes and what users publish: there is no classic `EventBus`, no logging through the stream (ohra logs through Python's `logging`), and no `SuppressedDeadLetter`: a dead letter whose message is a `DeadLetterSuppression`, as the cluster's heartbeats and join handshake are in Pekko, is logged at debug level and not published, where Pekko publishes it wrapped in a `SuppressedDeadLetter`, so a crashed member does not flood a `DeadLetter` subscriber until it is downed. `Subscribe` takes the event class, where Pekko reads it from a class tag. `DeadLetter`, `UnhandledMessage` and `Dropped` have no `sender`, since ohra messages carry none. A dead letter whose message is itself one of these events, or an `EventStream.Publish`, is only logged too, never published again, so a subscriber that is stopped or full cannot make the stream loop, a message adapter included. A dead letter to a message adapter, a timer or a `pipe_to_self` carries the message as it was sent, not the wrapper that delivers it. A reply that arrives after its ask has completed or timed out is only logged, not published. The stream is local to one system, as Pekko's.
- `ManualTime.time_passes` lets the actors settle before each due job: it waits until every actor has an empty mailbox and is waiting for its next message and every other task (a stream's, for one) waits on a future, with no callback left in the event loop's ready queue to wake one, or 100 ms of real time. Pekko sleeps 100 ms once and then runs every due job back to back, so a timer that leads an actor to start another inside the window fires here every time. Virtual times are rounded to nanoseconds, as Pekko counts whole milliseconds, so ten steps of 0.1 s reach a timer at 1 s. A repeating job cancelled while it runs is not rescheduled, and a job that raises is logged. On the manual clock run actor timers, backoff delays, a backoff's `reset_after` and the timeouts of `system.ask` and `ctx.ask`; the plain `ask` function takes `scheduler=`. So do the stream stages `Source.tick`, `throttle`, `grouped_within` and `ActorFlow.ask`'s timeout ([chapter 13](13-streams.md#time)). A task that never waits on a future, such as a loop of `sleep(0)`, keeps the loop from settling and leaves `time_passes` to the 100 ms fallback. Coordinated shutdown's phase timeouts, management's HTTP and health-check timeouts, the restart window of `with_limit` and the probes' deadlines stay on real time.
- The multi-node test kit runs every node in one process, on one event loop: each role is an `ActorSystem` and its body a task of one `asyncio.TaskGroup`, and the first role's controller serves the barriers by direct calls, with no connection to a conductor. Pekko runs one JVM per role, each with a player connected to the conductor over TCP. The nodes' own messages still go over TCP.
- `MultiNodeConfig.common_config` and `node_config` take `ActorSystem` keyword arguments in place of HOCON. The runner sets `name` and `address`, and the config raises `ValueError` when given either.
- There is no `deploy_on` or `deploy_on_all`, since ohra has no remote deployment.
- A body that raises fails the spec at once: the other bodies are cancelled, and the test raises an `ExceptionGroup` that names the role, `role second failed`. In Pekko the other nodes go on until a barrier fails.
- `disconnect` and `abort` close the links between two nodes, gracefully or by abort, and the next message opens a new connection. Pekko's `Player` ignores the `DisconnectMsg` they send (a `FIXME` at `Player.scala:285`), so in Pekko they do nothing. Since they act on the remoting here, they need `test_transport(on=True)` and raise `RuntimeError` without it, as `throttle`, `blackhole` and `pass_through` do.
- Throttle rates count the bytes of ohra frames, the 4-byte length prefix included, where Pekko counts the bytes of its own encoding, so one rate paces a different number of messages. A frame whose wait for tokens under `throttle` runs out is delivered anyway, on send and on receive, as Pekko's inbound `Dequeue` does; Pekko's outbound retry can stall on a frame larger than the bucket. If the mode was replaced during the wait, the frame is admitted by the new mode instead. A waiting frame tries again at least every millisecond, since Pekko's `timeToAvailable` can be 0 or less after a frame larger than the bucket has borrowed tokens.
- With the test transport on, outbound frames wait on an unbounded queue per peer, so the 16 MiB bound of the remoting entry does not apply and nothing past it becomes a dead letter. The frames queued for a peer whose connect fails are dropped without a `DeadLetter`.
- The conductor's operations have no query timeout: in one process each returns as soon as its effect has happened, so Pekko's `query-timeout` has no counterpart. `disconnect` and `abort` return once the links are closed, and `exit` once the system has crashed. `shutdown` takes the node out of the barriers and out of `get_nodes()` at once, as Pekko's controller does on `Terminate`, and starts the termination without waiting for it; with `abort=True` it waits for the crash.
- When a barrier fails, for a `ClientLost` for one, every pending `enter_barrier` raises, the lost node's own wait included, which Pekko leaves unanswered; in one process an unanswered wait would hang the run. For the same reason, an `enter_barrier` from a node that was removed, or never registered, fails at once with `FailedBarrier`, where Pekko's coordinator never answers it and the player times out.
- Each node's shutdown at the end of a spec waits at most `TestKitSettings.system_shutdown_default`, times `timefactor`, in place of Pekko's 15 second `shutdownTimeout`. A node that does not stop in time logs a warning and the run goes on, as Pekko's does with `verifySystemShutdown` off.
- `start_new_system` (Pekko's `startNewSystem`) is not ported. The durable specs of Distributed Data, ported from `DurableDataSpec` and `DurablePruningSpec`, start their extra systems with `ActorSystem(...)`, as Pekko's do. So `enter_barrier` on a node whose system has terminated raises `RuntimeError("TestConductor unavailable because system is terminated")`, without Pekko's suffix about calling `startNewSystem`.
- A role whose node is removed from the cluster has its system terminated, so it cannot enter the barriers after that: ohra's coordinated shutdown always terminates the system, where Pekko's `MultiNodeSpec` sets `coordinated-shutdown.terminate-actor-system = off` and the node keeps running. A spec that removes a node takes it out of the barriers with `test_conductor.remove_node(role)`, as the `ReplicatorPruningSpec` port does for third after its `Leave`.
- `mute_dead_letters`, `debug_config` and the perf flames (`PerfFlamesSupport`) are left out of the multi-node test kit: ohra logs dead letters, `debugConfig` turns on Pekko's loggers, and the perf flames run `perf` on a JVM.
- `SharedArray` ownership is a convention: whoever holds the handle owns the segment, sending it transfers ownership, and the owner calls `unlink()` once. A process that crashes while owning a segment leaks it. The resource tracker is kept out of it, with `track=False` on Python 3.13+ and by unregistering each segment on 3.12, so a process that only reads a segment no longer unlinks it when it exits.
- Distributed Data's types (`ohra.cluster.ddata`) are ported without the symbolic operators and the `(implicit node)` forms (`PNCounter`'s `:+` and `decrement(n)(implicit node)`, for one): only the named methods exist, taking a `SelfUniqueAddress` where Pekko takes a node. The `@InternalApi` overloads that take a bare `UniqueAddress` are `_`-prefixed methods (`_increment`, `_decrement`, `_with_value`, `_create`, `ORSet`'s `_add`, `_remove` and `_clear`, `ORMap`'s `_put`, `_update`, `_remove` and `_remove_key`, `_put`, `_increment` and `_decrement` on `LWWMap` and `PNCounterMap`, and `ORMultiMap`'s `_put`, `_remove`, `_add_binding`, `_remove_binding` and `_replace_binding`). `ORMap`'s `updated(node, key, initial)(modify)` is `update(node, key, initial, modify)`, with `modify` last, as Pekko's Java `update` has it, and replacing an `ORSet` value with `put` raises `ValueError` where Pekko throws `IllegalArgumentException`. `LWWMap.put` takes Pekko's implicit clock as `clock=default_clock`. `PNCounterMap` has no `incrementBy` or `decrementBy` and no `(implicit Cluster)` forms: `increment(node, key, delta=1)` and `decrement` take a `SelfUniqueAddress`, and its `entries` and `get` hold `int` where Pekko has `BigInt`. `ORMultiMap` has no `addBindingBy`, `removeBindingBy` or `replaceBindingBy` (they take an implicit node), and merging its two sub-types raises `ValueError` where Pekko throws `IllegalArgumentException`. `LWWMap`, `PNCounterMap` and `ORMultiMap` have no `getEntries` or `getValue` (Java API). Pekko's `apply` factories are dataclass defaults, `empty`, `VersionVector.create` and `LWWRegister.create`. `VersionVector`'s spellings differ: `<>` is `is_concurrent`, the `Ordering` members are lower case (`after`, `before`, `same`, `concurrent`), `VersionVector` is unhashable, and its `==` compares as Pekko's does, so a `OneVersionVector` equals a `ManyVersionVector` of the same entries. The wire format is the JSON of `@remotable`, not Pekko's protobuf `ReplicatedDataSerializer`: the delta ops are `@remotable` too and cross the wire in that JSON (below), and the encoding keeps insertion order, so two equal values can encode to different strings where Pekko's bytes are canonical. The `Replicator`'s digests hash a canonical form of this encoding instead, with every set's elements and every map's entries sorted, so equal data on two nodes has equal digests and stops being gossiped, where Pekko hashes its protobuf serialization. Values that are equal in Python but encode differently in JSON (`1`, `1.0` and `True`; `0.0` and `-0.0`) digest differently, so a set holding `1` on one node and `1.0` on another never converges; Pekko would treat an `Int` 1 and a `Double` 1.0 as distinct elements too. The data types' specs were ported before the `Replicator`, so their "unapply extractor" cases, which Pekko writes against `Replicator.Changed`, check value and key equality only, plus `case ORSet(elements)` and `case ORMap(entries)` (likewise `LWWMap`, `PNCounterMap` and `ORMultiMap`), which their `__match_args__` give as Pekko's `unapply` does. Pekko's Distributed Data samples are ported to `examples/distributed_data`: the cache picks its key with `crc32`, as Python's string hash differs between processes; the metrics measure peak resident memory against physical memory, where Pekko measures JVM heap, and keep their state in behavior parameters, where Pekko uses `var`s. The soak there is ohra's own, with no Pekko counterpart, and it compares what a reader of each node sees (the entries of an `LWWMap` or `PNCounterMap`, else the whole value), not whole data, since an `ORSet` merge rewrites its dots and a delta-merged state differs structurally from a full-merged one with the same entries, as Pekko's does.
- The `Replicator` is one typed actor whose handlers port classic `Replicator.scala` function for function, where Pekko runs the classic Replicator behind a typed facade. It ports membership tracking, the read and write aggregators, delta propagation, read repair, Status/Gossip anti-entropy and the pruning of removed nodes. `ReplicatorSettings` is a frozen dataclass with every duration in seconds, set as `ClusterSettings(distributed_data=...)`, not HOCON under `pekko.cluster.distributed-data`, and has no settings for the parts not ported. `DataEnvelope.merge(other, now)` takes the time as a parameter, where Pekko reads `System.currentTimeMillis()` inside `merge` to drop obsolete `PruningPerformed` markers; the Replicator passes its wall-anchored clock, the one the used timestamps of `expire_keys_after_inactivity` read (below), so `ManualTime` drives marker expiry in tests. The all-reachable clock that times `max_pruning_dissemination` adds up the scheduler's time, where Pekko adds up `System.nanoTime()`, so `ManualTime` drives it too. Delta propagation follows `Replicator.scala` and `DeltaPropagationSelector.scala` function for function, with these differences. The delta ops of `ORSet` and `ORMap` (`AddDeltaOp`, `RemoveDeltaOp`, `FullStateDeltaOp`, `DeltaGroup`, `PutDeltaOp`, `UpdateDeltaOp`, `RemoveKeyDeltaOp`) are `@remotable` under explicit names, `ORSet.AddDeltaOp`, `ORMap.PutDeltaOp` and so on, because the registry keys on the class name and the short names collide; with `Delta`, `DeltaPropagation` and `DeltaNack` they are JSON, not Pekko's protobuf. `Delta`'s first field is `envelope`, where Pekko's is `dataEnvelope`. `DeltaPropagation` has `from_node` for `_fromNode` and a fourth field, `reply_to`, as the other wire requests have: the write aggregator's adapter for the node receives its `WriteAck` or `DeltaNack`, where Pekko answers through `sender()`, and a `DeltaNack` makes the aggregator send that node the full `Write`. A tick's propagation has no `reply_to`. A `DeltaPropagation` larger than the remoting frame (`MAX_FRAME`) is not split: it is dropped with an error log and full-state gossip repairs the value later, as Pekko's TODO leaves it. `max_delta_size < 1` raises `ValueError`, with the other settings' checks, where Pekko does not check it. `TestFullStateGossip(enabled)` is a message of `Replicator` rather than of `Replicator.Internal`, and, as in Pekko, the Replicator handles it while it loads durable data too. `NoDeltaPlaceholder` is the module-level `NO_DELTA_PLACEHOLDER`. A `pruning_interval` of `0` or less turns pruning off, as Pekko's `pruning-interval = off` does. `PruningState` has no `estimatedSize`: the sizes that split gossip and are logged are measured on the canonical JSON, which includes the pruning markers. Merging into a deleted envelope drops its pruning markers, which Pekko keeps on the deleted envelope; nothing reads them, since pruning skips deleted data and a deleted envelope's digest is fixed. `ReadFrom(1)` and `WriteTo(1)` are accepted and answered from the local node, where Pekko requires `n >= 2`. The wire requests (`Read`, `Write`, `ReadRepair`, `Status`, `Gossip`) carry a `reply_to`: an aggregator sends each request with a message adapter of its own that names the node, where Pekko answers through `sender()` and reads its address. Status chunks are chosen by the CRC-32 of the key id, where Pekko uses `String.hashCode`, because Python's `str` hash is salted per process. A non-durable `Delete` that fails through `WriteNack`s replies `DeleteFailure`, where Pekko replies `UpdateTimeout`, which a typed `DeleteResponse` cannot carry; a durable one replies `StoreFailure`, as Pekko does. A `ReadResult` whose data cannot merge with the local value, being of another type, makes the read aggregator reply `GetFailure` at once; Pekko's aggregator throws, restarts, and leaves the caller to its timeout. When an ask of `ReplicatorMessageAdapter` outlives its `unexpected_ask_timeout`, the adapter hands the `response_adapter` a `GetFailure`, `UpdateTimeout` or `DeleteFailure` for the request's key, where Pekko throws the `AskTimeoutException` in the actor: an exception in an ohra adapt function is only logged, so the timeout would pass in silence. A timeout of `ask_replica_count`, which has no failure reply, is only logged. `with_replicator_message_adapter(factory, unexpected_ask_timeout=20.0)` takes the timeout as a parameter, where Pekko reads `replicator-message-adapter-unexpected-ask-timeout` from config. Subscribers are local only: `Changed`, `Deleted` and `Expired` are not `@remotable`, so a notification to a subscriber on another node is dropped with an error log, where Pekko serializes them. Only local actors and their message adapters are watched, so a remote subscriber is not removed by its termination either, only by `Unsubscribe`. The used-timestamp clock of `expire_keys_after_inactivity` is the scheduler's time plus the gap from the loop's clock to `time.time()`, re-read on every read. On the real scheduler it is wall time, as Pekko's `System.currentTimeMillis` is, so it follows wall time after a container freeze, and `ManualTime` still drives it in tests. Durable storage ports `DurableStore.scala` and the durable branches of `Replicator.scala`, with these differences. The default store is `sqlite_durable_store`, on the standard library's `sqlite3` and in the core, where Pekko's is `LmdbDurableStore`; its file is `<dir>/ddata.db` and it has no `map-size`. Its blocking calls run in `asyncio.to_thread`, awaited in the store actor's handler, so the store handles one message at a time as on Pekko's pinned dispatcher; there is no `use-dispatcher` or `pinned-store`. The store is a behavior factory, `ReplicatorSettings.durable_store`, where Pekko names a class in `store-actor-class` and builds it from a `Config` or `withDurableStoreProps`; the options of the SQLite store are its parameters, set with `functools.partial`. The protocol is typed: `LoadAll` carries a `reply_to`, where Pekko answers `sender()`. A stored value is the `@remotable` JSON, not protobuf, of a `DurableDataEnvelope`, which keeps the `PruningPerformed` markers only, as Pekko's protobuf does. A store whose load fails raises `LoadFailed` and stops, as does a store that fails later; the Replicator watches it and stops on its `Terminated` with an error log, where Pekko reaches the same end through a supervisor decider and `Terminated`. A store that restarts is not supported: under the default supervision it stops. While it loads, the Replicator drops its clock tick, where Pekko stashes it; the first tick after the load covers the time that passed. A non-local durable `Delete` takes `DeleteSuccess` as the store's reply: Pekko's `receiveDelete` sends the aggregator a `StoreReply(DeleteSuccess, StoreFailure, ...)` but its write aggregator matches only `UpdateSuccess`, so each such delete waits for its timeout; ohra's aggregator accepts either. `Expire` also drops the write-behind value pending for each expired key, so the flush that follows does not write an expired key back, where Pekko's does. `StoreFailure(key)` and the other replies carry no request context, which ohra's commands do not have. `DistributedData(system).replicator` is, as Pekko's, dead letters when the cluster has terminated or the node lacks the configured roles; the fallback is an `EmptyLocalActorRef` at `/deadLetters`, and `DistributedData(system).is_terminated` is true.
- The coordination lease is Pekko's `Lease`, `LeaseSettings`, `TimeoutSettings`, `LeaseUsageSettings` and `LeaseProvider`, with these differences. `LeaseProvider(system).register(implementation, factory, ...)` takes the place of loading `lease-class` by name, and the factory takes only the `LeaseSettings` and closes over the system, in place of Pekko's optional `ActorSystem` constructor parameter. `lease_config` holds only the registered mapping, not the timeouts or `lease-class`. `TimeoutSettings.create` does the validation of `TimeoutSettings(config)`; the constructor does not validate, as Pekko's does not. An implementation that is not registered raises `ValueError` with no log, as Pekko's empty `lease-class` does; a factory that raises is logged at ERROR and re-raised, as Pekko's failed class load is. Pekko's two `acquire` overloads are one method with an optional callback. The Java DSL and `LeaseAdapter` are not ported. In the test kit, `TestLease.initial_promise` is an `asyncio.Future` that `acquire` awaits through `asyncio.shield`, so a cancelled acquire leaves it pending; `TestLeaseActor` takes `Request(request, reply_to)` in place of classic `sender()`; and it restarts on an unknown `ActionRequest`, as the classic default does. Only sharding's shards acquire a lease.
